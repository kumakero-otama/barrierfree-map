Project overview

次のStepByを、
3つの仕事に分ける。

点字ブロックデータをOSMへつなぐこと、運用基盤をクラウドへ移すこと、そして日々の使いやすさを整えること。混ざっていた作業を3本の流れに整理しました。

01OSM直接統合・Valhalla廃止調査 → 方式決定 → 新規・既存データ移行 02クラウドサーバー移行移行条件確定 → 選定・費用相談 → 実移行 03その他の仕様・運用変更規約公開、UI1移行、協力者への連絡

Recommended order / 推奨する全体順序

  1. 調査と要件確定Valhallaの役割、OSMへの書込み条件、非公開情報を確認
  2. 仕様変更を実装新規データ統合、既存データ移行、UIなどを完成
  3. クラウドを決定必要性能と費用を確定し、松田先生へ相談
  4. 移行・検証バックアップ後に移行し、動作と公開範囲を確認

01

OSM直接統合・Valhalla使用中止

最大の技術変更。調査を終えてから、新規データ、既存データの順に進めます。

完了した2件の調査結果と、現行サービスを止めない移行計画をまとめています。 調査レポートを開く →

決定済み仕様

ここまでの検討で、次の内容を基本方針として確定しました。

ブラウザ側フィッティング現在地から約1km以内の歩行可能なOSM Way・Nodeをプリロードし、Web Workerで処理する。
リアルタイム選択条件GPS点に最も近い歩道または道路を候補とし、歩道を最優先。前回選択したWayとの連続性も考慮する。
確定時の経路記録全体を再計算し、OSM上で接続された、矛盾のない一つの経路とWay ID列を確定する。
Way途中の開始・終了記録開始点・終了点を既存Way上へ投影し、必要なNodeを作ってWayを分割。対象区間だけへ点字ブロック情報を付与する。
OSMタグ独立歩道Wayには tactile_paving=yes。道路中心線の場合は sidewalk:left/right:tactile_paving=yes など、OSM上の表現に合わせる。
StepBy由来の記録変更セットへ created_by=StepBy、source=survey、説明用commentを付与。独自のオブジェクトタグはコミュニティ確認後に判断する。
StepByサーバー保存内部ユーザーID・記録日時・確認日時・変更セットID・Way ID/Version・開始終了Node ID・順序・タグ・形状照合情報を保存する。
公開範囲と安全な移行StepByユーザーIDはOSMへ公開しない。新旧同時計算、限定利用、自動フォールバックを経てValhallaを最後に停止する。
OSM送信の禁止条件プロジェクト管理者の明示的な許可があるまで、本番OSMへのマージ機能を有効化せず、実データを一切送信しない。
マージ履歴と取消し送信要求、確認者、対象、変更内容、結果、changeset ID、エラー、取消しまで全イベントを追記型で保存する。履歴は削除・上書きしない。取消しは元の編集を消すのではなく、反対変更を新しいchangesetとして送る方式にする。
開発リポジトリ・ブランチ新しいリポジトリは作らない。フロントはStepBy内のUI10・UI11等、バックエンドはbarrierfree-mapの常設devブランチで開発する。
開発サーバーの分離本番と別フォルダ・別プロセス・別ポート・別DBで稼働。最初はTailscale Serve、GitHub Pagesからの結合試験時はFunnelの10000番を利用する。

先に確認すること

  • Valhallaが現在行っている処理を特定する完了。1点スナップと軌跡全体のマップマッチング・Way ID取得を確認。調査結果を見る
  • ブラウザ側でフィッティングを代替できるか検証する完了。条件付きで実現可能。無停止の段階移行案を作成。移行案を見る
  • 点字ブロックを含むWayをOSMへ直接マージできるか確認する実装面の確認は進展。Way分割案、changeset送信、Version競合停止、取消送信のコードを作成済み。残りはOSM認証方式、レビュー運用、コミュニティ確認。
  • PostgreSQLへOSM IDだけを保存する方式を確認する座標やタグを複製せず、OSMを正として照合できる構成を検討。
  • 公開・非公開データを分離できるか確認する点字ブロックはOSMへ。PROモードの柵・塀などと日常情報は公開しない。
  • StepBy IDをOSMデータへ付与できるか確認するWikidata項目の作成可否、OSMタグとしての適切性、コミュニティ方針を確認。
  • OSM公式アプリで地図情報を編集してみる完了済み。

方式決定後に実施すること

  • 開発用ブランチと作業領域を準備する完了。フロント・バックエンド双方にdevブランチと別worktreeを作成し、GitHubへpush済み。
  • 開発バックエンドを別プロセスで起動する完了。本番3000番とは別に、localhost限定の3100番・別PM2プロセスで稼働。本番DB設定は渡していない。
  • 開発データと外部接続先を分離する完了。本番DBと同じ構造の開発専用DBを新規作成し、UI10の読み書きを開発DBだけへ分離。OSM送信はサーバー機能フラグで無効、認証情報も未設定。
  • 開発APIのTailscale接続を設定する完了。10000番はFunnel経由で開発API（localhost:3100）を公開し、10001番はtailnet内限定ServeでUI10（localhost:3200）を配信。許可したOrigin、認証、レート制限などの防御を適用している。
  • Funnel公開前の開発API防御を実装する完了。署名付きログイントークン、本人ID固定、履歴一覧の管理者キー、IP・ユーザー単位の二重レート制限、本文サイズ上限、Origin制限、異常アクセスログ、秘密鍵のGit分離を実装。未認証・偽トークン・ID偽装・大量アクセス・過大データの拒否を試験済み。
  • 新API検証用フロントをUI10以降へ実装する完了。UI10、開発API URL、開発専用Service Worker・キャッシュ、DEV表示を本番UI0から分離。
  • OSM歩行ネットワークの取得・キャッシュを実装する実装中。約1km圏の歩行可能WayをOverpassから取得し、Way ID/Version・Node ID・タグ・形状を返す開発API、5分サーバキャッシュ、IndexedDB保存まで実装。タイル差分取得・圧縮は未実装。
  • StepBy専用ブラウザフィッターを実装する実装中。60m以内の線分投影、歩道優先、同一Way・共有Node接続優先をUI10へ実装し単体確認済み。空間インデックス、方位評価、Web Worker化は未実装。
  • 確定時の経路全体最適化を実装する実装中。開始・終了のWay途中位置と、共有Nodeで連結されたWay ID列を生成できる段階。GPS点列全体の確率的再最適化は未実装。
  • Valhallaとのシャドー比較機能を実装する実装中。UI10で同一GPSを新旧同時計算し、GPS・Valhalla・ブラウザ版・結果差を地図へ色分け表示。Way ID、位置差、歩道判定、連続性、計算時間、保存履歴番号を比較パネルへ表示し、実験DBへ全件保存できる。経路全体の比較集計と合格基準判定は未実装。
  • OSM認証と変更確認画面を実装する実装中。OSM OAuth 2.0＋PKCEの開始・コールバック・状態確認・連携解除APIと、UI10プロフィールの連携画面を実装。アクセストークンは開発DBへ暗号化保存し、認証開始・成功・失敗・解除は秘密情報を除いて追記型監査履歴へ保存する。Google認証はStepByログイン、OSM認証は初回の編集権限取得として分離。次はOSM側でStepBy OAuthアプリを登録してClient IDを開発設定へ追加し、OSM開発環境で認証だけを確認する。変更案確認UIは実装済みだが最終送信確認UIは未実装。実送信は引き続きロック中。
  • Wayの途中分割処理を実装する実装中。開始・終了Node、正逆方向、複数Way、対象区間だけの tactile_paving=yes、元タグ継承に加え、Relationのmember順・forward/backward role・Relationタグの引き継ぎを偽データで自動試験済み。残りは道路中心線用タグの分岐。
  • OSM変更セットの作成・送信APIを実装する完了。changeset作成、Node・Way一括送信、ID・Version取得、changeset終了を実装。Version競合時は送信前に停止する。現在は機能フラグ無効で必ず423となり、実OSMでは未試験。
  • StepBy記録とOSM処理を1対1で紐付ける完了。1記録＝1変更案＝1送信changeset＝最大1取消changesetの単純な表を開発DBへ実装。2件目の変更案・取消案は拒否し、状態を draft / merged / revert_draft / reverted / failed / conflict で管理。詳細画面にも状態とIDを表示する。
  • OSMマージ取消APIを実装する完了。record_idから元の変更案と監査履歴を特定し、反対変更を新しい取消案として作成するAPIへ整理。送信済みの場合は現在Version確認後に新しいchangesetとして取消す設計。機能フラグ無効のため実送信は不可、実OSMでは未試験。
  • OSM再編集後の追跡・再照合を実装する後からWayが再分割・統合された場合、変更セット・Node・形状情報を使って対応先を更新する。
  • OSM開発環境で編集テストを実施するWay分割、Relation、競合、キャンセル、再送、ID返却、権限エラーを確認。本番OSMへはテストデータを送らない。
  • OSMコミュニティへ方式を確認するタグ付け、StepBy由来の表現、支援型編集・大量編集の運用を事前相談する。
  • 限定利用から段階的に切り替える開発者、協力者、一部利用者、標準利用の順に拡大。低信頼・データ不足・処理失敗時はValhallaへ自動退避。
  • 既存データ移行用の別タスクリストを作成する件数、品質、重複、マージ可否、公開対象を確認し、少量の試験から始める。
  • 既存の点字ブロックデータをOSMへマージする新規データ用機能の安定稼働とコミュニティ確認後、結果を確認しながら段階的に実行。
  • Valhallaを停止するブラウザ版とOSM統合が合格基準を満たし、一定期間の安定稼働を確認してから停止。設定と復旧手段は保管する。
次に実施： OSM側でStepByをOAuthアプリとして登録し、Client IDを開発サーバーへ設定して、OSM開発環境で「初回認証→StepByへ戻る→連携状態表示→解除」を確認する。認証確認でもOSMへの地図変更は送信しない。その後、道路中心線Wayに対する点字ブロックタグの分岐へ進む。
重要な順序： Valhallaは先に止めず、端末側フィッティングとOSM保存が同等以上に動くことを確認した後で停止します。
02

クラウドサーバー移行

ブラウザフィッティングへの移行を完了し、Valhallaを廃止した構成を前提に検討します。現時点では移行先・構成とも未定です。

OPTION A

VPSをまるごと移行

現在のサーバー構成を、新しいクラウドVPS上へまとめて移します。

  • APIとデータベースを1台で運用
  • 現在の構成に近く、移行手順が分かりやすい
  • OS・セキュリティ・バックアップを自分たちで管理
OPTION B

DBとAPI実行環境を分ける

マネージドデータベースと、APIを動かすクラウドサービスを個別に契約します。

  • DBのバックアップや更新をサービス側へ任せやすい
  • APIだけ個別に増強・変更できる
  • 複数サービスの料金、接続、障害対応を比較する必要がある

選定・相談

  • 移行前に完了させる仕様変更の範囲を確定する「全て完了」の判定条件をチェックリストにする。
  • Valhalla廃止後のクラウド要件を決めるAPI、PostgreSQL、画像、ログ、バックアップ、運用負荷、月額上限、OSM連携を整理。Valhalla用のCPU・メモリ・タイル容量は含めない。
  • 2つの移行方式を比較する
    • 案A：VPSへAPI・DBをまとめて移行
    • 案B：マネージドDBとAPI実行サービスを個別契約
    • 料金、管理負荷、バックアップ、拡張性、障害時の切り分けを比較
  • 構成とサービスを決定する移行先・構成未定
  • 移行費用と継続費用を見積もる
  • 松田先生へ費用負担を相談する「可能であればご支援いただきたい」という依頼文と、見積りを準備。

移行作業

  • 移行手順と切戻し手順を作成する
  • データベースと設定をバックアップする
  • クラウド環境を構築し、アプリとデータを移行する
  • 本番切替え前に総合テストする認証、記録、OSM連携、非公開情報、性能、バックアップ復元を確認。
  • 本番を切り替え、移行後を監視する
開始条件： 01のブラウザフィッティング・OSM統合が安定し、Valhallaを廃止できていること。03の必要な仕様変更が完成し、移行構成・サービス・費用の承認が取れていること。
