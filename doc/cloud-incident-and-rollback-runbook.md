# StepBy クラウド障害対応・切戻し手順

更新日: 2026-08-13  
対象: Google Cloud上の開発版UI10/API/PostgreSQL/Caddy

## 1. 最初に守ること

- 障害中も、OSM監査履歴を削除・上書きしない。
- 監査履歴を開始前に保存できない場合、OSM送信を停止する。
- DBバックアップの復元でOSM編集を巻き戻さない。OSM取消しは現在Versionを確認した反対変更として扱う。
- 原因が分からないまま旧サーバーとクラウドAPIの両方へ書き込ませない。
- 秘密情報をログ、画面、Git、作業メモへ貼らない。

## 2. 5分以内の切り分け

1. 管理画面の「クラウド稼働状況」でAPI、PostgreSQL、Caddy、バックアップ、ディスク、メモリ、OSM失敗数を確認する。
2. 公開確認は `https://stepby-api-8-229-191-182.sslip.io/api/config` を開く。
3. VMでは次を確認する。

```sh
sudo systemctl status stepby-dev postgresql caddy --no-pager
sudo journalctl -u stepby-dev --since "30 min ago" --no-pager
df -h /
free -h
```

4. OSM送信に関係する障害では、先にサーバー側のOSM送信機能フラグを無効化し、APIを再起動する。StepBy記録そのものは端末キューまたはDBへ保持する。

## 3. 症状別の対応

### APIが応答しない

- `stepby-dev` の状態と直近ログを確認する。
- 設定・Secret取得・DB接続のどこで止まったかを分ける。
- 修正後はAPI設定、ログイン、記録保存、管理画面の順に確認する。
- 再起動だけで原因を隠さず、時刻と原因を運用記録へ残す。

### PostgreSQLへ接続できない

- PostgreSQLの状態、ディスク残量、接続数を確認する。
- DBが復旧するまでOSM送信を止める。監査履歴を保存できないためである。
- 復元が必要なら最新の日次バックアップを別の一時DBへ復元し、テーブル数と主要件数を確認してから切り替える。

### HTTPSまたはCaddyの障害

- Caddy状態、証明書更新ログ、80/443番ポートを確認する。
- HTTPへ格下げしない。GitHub Pagesからの認証・API通信はHTTPS前提である。

### ディスク・メモリ不足

- ディスク65%で注意、80%で対応開始、90%で新規書込み停止を検討する。
- 削除前に、対象が再生成可能なログ・キャッシュか確認する。DBや監査履歴を直接削除しない。
- メモリ不足はプロセスRSS、DB、同時処理数を確認し、再発するならVMサイズを見直す。

### OSM OAuth・API・Version競合

- OAuth未連携・権限取消しは自動再送せず「連携が必要」として停止する。
- 429、408、5xx、通信断だけを一時障害として待機再送する。
- Version競合はchangeset作成前に停止し、第三者編集を上書きしない。
- 監査開始保存に失敗した場合はOSMへ一切送信しない。
- changeset作成後にuploadが失敗した場合は空changesetを閉じ、記録と失敗履歴を残す。

### Overpass・OSM表示データの障害

- 1kmのフィッティング道路網と10kmの表示用点字データを別々に確認する。
- 一方の読取障害を、記録保存やOSM送信成功と混同しない。
- 既存キャッシュがある場合は表示・記録を継続し、上流復旧後に更新する。

## 4. アプリ版の切戻し

1. 障害時刻、現在のフロントコミット、APIコミット、DB状態を記録する。
2. OSM送信を無効化し、処理中ジョブと監査履歴を確認する。
3. GitHub PagesのUI10接続先を、確認済みの直前コミットへ戻す。
4. APIは `/srv/stepby/releases/` の確認済みリリースへシンボリックリンクを戻し、`stepby-dev` を再起動する。
5. `/api/config`、認証、読取、DB保存を確認してから利用を再開する。
6. OSM送信は監査、OAuth、冪等性、Version確認を再検証した後に別途有効化する。

## 5. DB復元を伴う切戻し

1. 障害中のDBを先に保全し、最新バックアップを別の一時DBへ復元する。
2. スキーマ数、主要テーブル件数、最新記録、OSM監査履歴を比較する。
3. 復元点以降に成功したOSM changesetがないか必ず照合する。
4. DB復元によってOSM側を過去状態へ戻そうとしない。不一致は追記監査と安全な取消し手順で解消する。
5. 管理者が復元点と失われる可能性のあるStepBy記録を確認してからDB接続先を切り替える。

## 6. 復旧完了条件

- API、PostgreSQL、Caddyがactiveである。
- HTTPS設定APIが200を返す。
- 開発DBへの読取・テスト保存が成功する。
- OSM監査履歴が欠損せず、処理中・失敗・競合が判別できる。
- 二重changesetが作られていない。
- バックアップの最新成功時刻と次回実行予定を確認した。
- 原因、影響範囲、対応、再発防止を運用記録へ追記した。
